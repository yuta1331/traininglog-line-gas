# ADR-0004: 送信元トークンをクエリパラメータで検証し、月次で自動ローテーションする

- ステータス: Accepted
- 日付: 2026-08-12

## 背景

[ADR-0002](0002-webhook-signature-verification-not-possible-on-gas.md) は「LINE の署名検証は素の Google Apps Script では実装できない」という事実を記録し、実装方式の決定を #32 に委ねた。本 ADR はその決定である。

守っている資産は**個人のトレーニング記録のみ**で、金銭も他人の個人情報も関わらない。偽造リクエストで起きうるのは次の2つ。

- **シート汚染** — デプロイURL **かつ** 許可ユーザーの `userId` を両方知っていれば、任意の記録を追記できる。喪失ではなく混入で、復旧は手作業で可能
- **クォータ焼き** — デプロイURLだけ知っていれば `doPost` を叩ける。許可ユーザー判定で弾かれるので `UrlFetch` は走らないが、シート読み込みは毎回走る

情報漏洩の経路は無い。`json書き出し` を叩かれても返信は `replyToken` 経由でしか届かず、`replyToken` は偽造できない。

## 決定

**Webhook URL のクエリパラメータ `t` に秘密のトークンを載せ、`doPost` の冒頭で照合する。トークンは月次のトリガーで自動ローテーションする。**

`doPost` は `e.parameter` を読めるので、ヘッダーが読めないという ADR-0002 の制約を迂回できる。

### この方式が証明できること・できないこと

**これは署名検証ではない。** 証明できるのは「このURLを知っている送信元から来たこと」だけで、「LINE から来たこと」ではない。コミットメッセージにも CONTEXT.md にも「署名検証を実装した」とは書かない。

エントロピーの観点では、**将来の漏洩に対して強度を足さない**。URLが漏れればトークンも一緒に漏れる。効くのは次の2点。

1. **過去の露出を締め直せる。** デプロイIDは既に LINEコンソール・ブラウザ履歴・ローカルの `.clasp.json`・過去の `clasp deployments` 出力に存在する。トークンはそのどれにも存在しない新しい秘密である
2. **秘密を安く回せるようになる。** 従来の唯一の秘密であるデプロイIDのローテーションは「新規デプロイ作成 → URL変更 → LINE再登録」という重い手順（[ADR-0003](0003-ci-only-no-cd.md)）だった。トークンならスクリプトプロパティの書き換えで回る

**副次的な効果**として、照合を JSON パースより前に置くため、トークンを持たない偽造リクエストはシート読み込みすら起こさなくなる。上記「クォータ焼き」は実質消える。

### ローテーションの手順

月次の時間主導トリガーで以下を実行する。認証はすべて既存の `LINE_CHANNEL_ACCESS_TOKEN` で足りる。

1. `GET /v2/bot/channel/webhook/endpoint` で登録中のURLと `active` を取得
2. `active:false` / endpoint 未設定 / URLに `t` が無い → **中止して throw**（事由を区別できるメッセージで）
3. **旧トークン C を「1で得た登録URL」から抽出する**
4. 新トークン N を `Utilities.getUuid()` で生成
5. スクリプトプロパティを `"C,N"`（2つとも受け付ける状態）に更新
6. `PUT /v2/bot/channel/webhook/endpoint` で N 入りURLを登録
7. `Utilities.sleep(120000)` の後、プロパティを `"N"` に刈り取り

**手順2 で「URLに `t` が無い」を中止条件にしている理由**は、ローテーションが「登録URLが自分のデプロイであること」を検証できないからである。`getUrl()` が使えず（後述）、base URL をどこにも保持しない設計を採った結果、`t` の無いURLが「自分のURLからトークンが剥がれた」のか「誰かが Webhook を別の場所へ向けた」のかをコードは区別できない。正体不明のURLにトークンを刻印するのは、異常を塗り潰す操作になる。`active:false` の中止が「Bot が止まっているのでローテーションが無意味」なのに対し、こちらは「外部の介入の痕跡を消さない」であり、理由が違う。

**5→6 の順序と、3 の「旧トークンは登録URL由来」がこの設計の安全性を担っている。**

- 6 が失敗しても、LINE は旧URL（C）を向いたままで GAS は C も N も受け付けるため、Bot は動き続ける
- 3 をプロパティ由来にすると壊れる。6 が失敗した翌月、プロパティ末尾（N）を現行とみなして `"N,M"` を書くと、**LINE が実際に使っている C が受付集合から消えて全停止する**。登録URL由来にすることで「LINE が使っているトークンは常に受付集合にある」が手順の構造から保証される

失敗時は**ロールバックしない**。旧URLも新URLも同じデプロイを指すので、到達性は1ビットも変わらず、効かない手当てになる。`"C,N"` のまま残して次回の実行に委ねるのが安全側。

`Utilities.sleep(120000)` は**キャッシュ遅延に対する防御**であり、疎通確認の付属物ではない。LINE のドキュメントはURL変更の反映に「最大1分」と書くが目安であって保証ではないため、倍を取っている。

### 検証できない前提を承知で受け入れたリスク

刈り取り後にキャッシュ遅延で旧URL宛の配信が届くと、そのリクエストは拒否される。帰結は**メッセージ1通の静かな喪失**（エラーではなく無応答として現れ、返信が無いことで気づいて再送できる）。月1回・深夜帯・キャッシュ遅延が120秒を超えた場合のみという条件の積であり、上記の脅威モデルに対して許容する。

将来この喪失が実際に観測された場合の逃げ道として、**ワンショットトリガー（`.after(1h)`）で刈り取りを後送りする**案がある。`sleep` の延長は GAS の実行上限6分により実質4分が天井で、根本解にならない。

## 実測で判明した環境の制約

### LINE は GAS の 302 リダイレクトを追わない

Webhook URL の「検証」ボタン（実体は `POST /v2/bot/channel/webhook/test`）は、本番URLに対して**失敗する**。2026-08-12 に実測した文言：

```
エラー
ボットサーバーから200以外のHTTPステータスコードが返されました。(302 Found)

LINEプラットフォームから送信されたHTTP POSTリクエストに対してボットサーバーがステータスコード200を返すことを確認してください。
詳しくは、Messaging APIリファレンスのレスポンスを参照してください。
```

GAS のウェブアプリは 302 で `script.googleusercontent.com` へリダイレクトし、その先が 200 を返す。LINE はこのリダイレクトを追わないため、**LINE から見ると本プロジェクトへの配信は毎回「失敗」している**。

同じ文言がクエリパラメータの有無にかかわらず出ることも確認済みで、**クエリ文字列が原因ではない**。実際、`?t=test` を付けた状態で LINE から実メッセージを送ると、既読・シート更新・返信のすべてが通常どおり動作した。**Webhook の実配信は正常に届いている。**

この結果、当初の手順にあった「`webhook/test` による疎通確認を経てから刈り取る」というステップを**削除した**。機能しない検査を残すと、結果が制御フローに影響しないまま「疎通確認がある」と誤読させ、かつ毎月の偽アラームで本物の失敗通知を埋もれさせる。

### したがって Webhook 再送機能を有効にしてはならない

LINE の Webhook 再送は「ボットサーバーが 2xx を返さなかったとき」に発動し、既定では無効。上記のとおり本プロジェクトは LINE から見て**一度も 2xx を返していない**ため、**再送を有効にすると全メッセージが再送され、トレーニング記録が重複登録される**。

LINE 公式・第三者の解説記事はいずれも「Webhook 再送の有効化」を推奨しているため、将来これを踏む可能性が高い。**現状のコードのまま有効にしないこと。**

**ただしこれは ADR-0002 のような「原理的に不可能」ではない。** 重複排除に使う `webhookEventId`（ULID）と `deliveryContext.isRedelivery` は**リクエストボディ**に入るため、GAS でも読める。ヘッダーが読めないという制約はここには効かない。再送を有効にしたくなった場合は、**重複排除を実装することが前提条件**になる、というのが正確な位置づけである。

## 失敗の通知

ローテーションが失敗したときは `Logger.log` に記録して **throw する**。GAS の時間主導トリガーは関数が例外で終わるとオーナー宛に失敗通知メールを送るため、コードの追加なしで検知経路が手に入る。

**LINE の push メッセージで通知する案は採らなかった。** ローテーション失敗の原因が LINE API 側の障害である場合、通知もまったく同じ理由で失敗する — 通知経路が失敗原因と同じ依存を持つ。メールは LINE に依存しない独立経路である。

この案の下には「UserList シートのロール列が `管理者` の行を通知先にする」という設計があり、8ラウンドの検討を費やしたが、通知をメールに一本化したことで丸ごと不要になった。スプレッドシートに手打ちされた日本語文字列（末尾スペース・全角半角・表記揺れ）を通知経路の単一障害点にする形でもあり、採らなくてよかった。

メール通知が日次ダイジェスト設定のままでも**この設計は壊れない**。失敗時に残る `"C,N"` は構造上安全（Bot は動き続ける）ため、通知が1日遅れて失われるのは**ローテーションの衛生であって可用性ではない**。「今すぐ通知」への変更は推奨だが、必須ではない。

## その他の設計判断

- **プロパティ未設定は fail-closed。** `src/config.ts` の既存挙動に一貫させる。fail-open にすると検証を素通りして無防備な状態に黙って戻る。fail-closed なら Bot は止まるが、メッセージを送ればすぐ気づく
- **トークン不一致でも正常時と同じ応答を返す。** 区別可能な応答は、URLを掴んだ相手に「URLは当たり、トークンだけ違う」と教えることになる。プロパティ未設定時のエラーメッセージを外に出さないことも含む。ログには受信値のみを残し、期待値側のトークンは書かない
- **ローテーションの入口に `LockService` の `tryLock` を置く。** 月次トリガーと手動実行の衝突を防ぐ。ロック取得の失敗は**異常ではなく正常系**なので、ここで throw してはならない（良性の衝突を失敗メールにすると、上記の通知の信頼性を自分で削る）
- **`ScriptApp.getService().getUrl()` は使わない。** V8 ランタイム以降 `/dev`（HEAD）のURLを返すため、バージョン固定デプロイを本番にしている本プロジェクト（ADR-0003）では使えない。これを踏むとローテーションが本番の向き先を黙って `/dev` に変える。手順1の `GET` で LINE に登録済みのURLを読むことで回避している

## 採らなかった選択肢

- **前段に薄いプロキシを置く（ADR-0002 の選択肢1）** — Cloud Functions / Cloudflare Workers 等で `X-Line-Signature` を検証し、通過分だけを GAS へ転送する。正攻法だが2つ目のデプロイ対象とシークレット保管場所を作る。
  加えて、**プロキシは本 ADR の方式を内包する**。Worker を前に置いても GAS の `/exec` は世界中から叩けるままで、GAS 側で「プロキシ以外を拒否」する必要があり、ヘッダーが読めない以上それはクエリパラメータの共有秘密そのものになる。「正攻法」の実体は プロキシ＋クエリトークン であり、プロキシ単体では穴が塞がらない
- **`t` の無いURLを自己修復する** — 手順2で中止する代わりに、新トークンで登録し直して復旧させる案。ローテーションは月次なので、URLが失われた瞬間から自己修復が走るまで平均15日かかる。一方で人間は返信が来ないことに数日で気づいて手で直すため、**実際に短縮される復旧時間はほぼゼロ**で、確実に得られるのは「異常の痕跡の消去」だけになる。加えて上記のとおり、それは正体不明のURLへの刻印になりうる
- **刈り取りを次回実行の冒頭で行う** — 実行内で `sleep` せずに済む案。しかし定常状態で常に2つのトークンが有効になり、うち1つは1ヶ月古い。ローテーションの意味が薄れるため採らない
- **デプロイIDを作り直す** — 既に複数箇所に露出しているデプロイIDを新しくする案。トークンという新しい秘密が乗る以上、デプロイIDが既知でも防御は成立するため、ADR-0003 の重い手順に見合う追加の安全は無い
- **許可判定にロールを使う** — UserList シートのロール列（`管理者` / `ユーザー`）で許可を判定する案。リクエスト経路への変更になりスコープ外であることに加え、ロール列が空の行が1つでもあれば**次のデプロイでそのユーザーが黙って締め出される**

## 結果

- ADR-0002 は `Accepted` のまま据え置く。「GAS はヘッダーを読めない」という事実は覆っておらず、だからこそ署名検証ではなくトークンを採っている。`Superseded` を貼ると「もう読まなくていい ADR」と誤読され、その事実が失われる
- 実装は #32 の後続 PR で行う
- 導入は**無停止で可能**。fail-closed のため「デプロイ → LINEコンソール更新」の順では間が止まるが、逆順（プロパティ設定 → コンソールでURL更新 → デプロイ）なら止まらない。コンソール更新の時点で動いている旧コードは `e.parameter` を無視するため
- ただし**デプロイ直後に実メッセージでの疎通確認を必須とする**。2026-08-12 の実測で確認できたのは「クエリ文字列付きURLでも Webhook の実配信が届く」ことまでで、**GAS が `t` を `e.parameter` から実際に受け取れるか**は（documented behavior ではあるものの）まだ実測していない。fail-closed のため、万一外れると全停止として現れる
